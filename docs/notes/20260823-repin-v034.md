# Upstream re-pin `v0.3.2 → v0.3.4`

**2026-08-23.** Pin `c6b91b9e` (`v0.3.2`) → `b10bd5df` (`v0.3.4`), 151 commits
across two releases. Verdict: **PASS, 0 FP / 9204 files**, harness 97 fixtures /
0 unregistered extras, both standing exception tables still EMPTY — but only
after **two port-side fixes**, because the raw bump opened **50 false
positives** that the fixture harness could not see.

This is the first bump where **both re-sync halves of the ritual were no-ops**
and the bump was still not free. The lesson is the inverse of the `v0.3.2` one:
that bump's danger was in the DATA (`data/` overlay, the `sig/shims` trap) and
its logic delta was inert; this one's data is inert and the danger is in the
LOGIC — specifically in upstream *retracting* diagnostics, which turns
byte-identical port behaviour into false positives overnight.

### Most of the release is out of parity scope

`v0.3.4`'s headline is the **effect system** (`rigor effects`, ADR-103) and
`v0.3.3`/`v0.3.4` also add **`rigor unused`** (ADR-102). Both are new COMMANDS
behind opt-in config, and upstream states a project without an `effects:` block
gets a byte-identical `rigor check`. [ADR-0002](../adr/0002-diagnostic-set-parity.md)
scopes parity to `rigor check`'s diagnostic set, so neither is port work here;
they belong to the CLI-surface backlog, not to the pin.

The `check`-visible delta is **ten engine commits**. Their net effect on the
96-fixture corpus was **one** new reference diagnostic. Their net effect on 9204
corpus files was **50 false positives**. That asymmetry is the whole story of
this note: the fixture corpus grades what the port has already modelled, and it
cannot grade a retraction upstream just made somewhere the fixtures do not go.

### The feedback loop closed, and it closed ON US

**All five defect reports of upstream feedback batch 3** — filed 2026-08-09,
[note](20260809-deferred-slices-and-upstream-feedback.md) — are fixed in
`v0.3.4`: #316 (`263e55aa`), #317 (`91d8befd`), #318 (`9e55deae`), #319
(`189c498b`), #320 (`589ef996`). Three of the five were *reference FPs this
project adjudicated and declined to port* — the 2026-08-08 `Object`-bucket
adjudication counted "16 `Class.new do…end` toplevel-scoped block bodies, 2
`class << Const = Object.new` dropped bodies" as reference defects and
deliberately left rigor-rs matching them
([adjudication](20260808-object-bucket-adjudication.md)).

That decision was right, and it has a cost with a delay on it: the moment
upstream agrees and fixes the defect, "we match the oracle's bug" flips to "we
are louder than the oracle", with no code change on our side. **A filed upstream
issue is therefore a scheduled port obligation**, and the pin bump that lands the
fix is when it comes due. Worth checking the open-issue list against the release
notes as step 0 of the next bump rather than discovering it in step 7.

## Fix 1 — `Class.new do … end` is a class body (#319, 48 FPs)

Upstream `189c498b`. Ruby evaluates such a block with `self` bound to the
freshly created class, so a `def` inside it defines an instance method and
`attr_reader` runs as a class-level macro. The reference had always known that
through its `ConstantWriteNode` branch — the constant supplied the name its
discovery tables are keyed by — and away from that position
(`observer_class = Class.new do … end`) the body fell through to the enclosing
scope. At file top level that made `Scope#toplevel?` true, so every macro call
in the body warned as `call.unresolved-toplevel`.

rigor-rs matched that exactly. At the `v0.3.4` pin the same output is 48 false
positives, all in RSpec suites, all in the `Class.new(described_class) do … end`
/ `Module.new do … end` idiom:

| corpus | FPs | site |
|---|---|---|
| dependabot-core | 40 | `*/spec/dependabot/*/base_spec.rb` |
| concurrent-ruby | 8 | `spec/concurrent/edge/erlang_actor_spec.rb` |

**The port is one-sided on purpose.** Upstream's fix is mostly *identity*: a
synthetic `#<Class:path:line:col>` name, registered in the discovery tables so
the body's methods are reachable and `class_new_lift` can answer it instead of
`Singleton[Object]`. That half only ever makes the reference emit MORE, so it is
coverage, not FP safety, and it is recorded as such rather than built. What
rigor-rs needed is the scope half, and its `call.unresolved-toplevel` is
span-based: the block body of a `Class.new` / `Module.new` / `Struct.new` /
`Data.define` call with a literal block joins the class/module spans as a
NON-toplevel region (`meta_new_block_body_spans`, `crates/rigor-rules/src/lib.rs`).

Two boundaries were measured rather than assumed:

- **Only the block body.** The receiver and the arguments keep the enclosing
  scope, so `Class.new(parent_of(x)) { … }` still fires on `parent_of`. Oracle:
  fires at `1:15`.
- **The constant-write rvalue is carved OUT.** `A = Class.new { attr_reader :a }`
  still fires on the reference, because `StatementEvaluator` never routes a
  constant-write rvalue through the block-body narrowing #319 added — the
  reference's own asymmetry, stated in the commit and confirmed on a probe
  (`A = …` fires; `a = …`, `@a = …` and the bare expression form do not). Missing
  this would have traded 48 false positives for a silent hole in the commonest
  spelling of the idiom. `Outer::F = …` lowers to the recovery carrier (rigor-rs
  has no owned `ConstantPathWrite`), so it stays suppressed — a coverage gap,
  never an FP, and recorded here rather than fixed.

Fixture 96, plus three unit tests in `rigor-rules`.

## Fix 2 — `defined?`'s operand is not evaluated (#318, 2 FPs)

Upstream `9e55deae`. `defined?` inspects its argument statically and never runs
it, so nothing under a `DefinedNode` is reachable code; upstream stopped all
three of its engine tree-walks descending there. Two sweep FPs
(dependabot-core's `if defined?(git_dir)`, in `update_checker_spec.rb` and
`latest_version_finder_spec.rb`) plus two more shapes on a hand probe —
`defined?(s.frobnicate)` on a typed receiver, and an implicit-self call as the
operand.

**The obvious port is wrong, and the sweep would not have caught it.** Lowering
a `DefinedNode` to a leaf silences the calls — and also hides the local READS
under it, which promptly invented a fresh `flow.dead-assignment` FP on
`y = 1; defined?(y)`. The reference stays silent there: #318 touched its three
engine walks only, and `DeadAssignmentCollector#gather_read_names` does its own
`rigor_each_child` recursion, which still descends into a `DefinedNode`. So the
operand gets a CALL-SUPPRESSING recovery, not a leaf: calls are recursed
*through* rather than recorded, so a read in `defined?(foo(y))` still counts
(`collect_defined_operand_children`, `crates/rigor-parse/src/ast.rs`).

The parenthesised `defined?(a) && a.m` leaves the second call outside the
operand, where it stays live code — that follows from the parse, not from
anything in the fix; the bare `defined? a && a.m` binds lower than `&&` and
swallows the conjunction, which is the false positive the upstream issue cites.

Fixture 97, plus a `rigor-parse` unit test. One stale test row retired:
`class_narrowing_stage3b1_statement_form_matrix`'s `d24` pinned a narrowing fact
reaching a call inside `defined?`; there is no such call on either side any more.

## The one new coverage gap on the fixture corpus

`63_const_literal_harvest.rb:54` — upstream `1eda3dcf` / #356 now resolves a
constant through the ANCESTOR chain (`Module.nesting`, then the innermost
cresting scope's ancestors, then top level; the middle step was missing), so
`DAYS` in a class that merely `include`s the module defining it now folds to `7`.
The fixture's "STAYS SILENT" comment described the reference's old behaviour and
has been corrected in place. Probed alongside it: the same commit changes which
declaration WINS when a name exists on both an ancestor and at top level — the
ancestor now does, where the bare-name fallback used to take the top-level one.
rigor-rs still answers the top-level value, which keeps the `(rule, line, column)`
set identical on the probe but is a latent divergence the moment the two values
have different method surfaces.

Also probed silent-or-gap, no FP: `Ractor.make_shareable`-style `[T] (T) -> T`
argument-position binding (`7f043419`), `Array.new(n) { … }` element typing
(`91d8befd`), `Tuple`/`HashShape` `inspect`/`to_s` folding (`6e1a656d` — same
diagnostic set, more precise message text, which ADR-0002 permits), and the
`class << Const` singleton body (`589ef996`).

## For the next bump

The ritual's step 5 says to review the snapshot diff for newly-appearing
reference diagnostics. That is necessary and it was not sufficient: it surfaced
ONE line here, while the two real findings were retractions — diagnostics the
reference STOPPED emitting, which a snapshot diff of the fixture corpus shows as
nothing at all, because rigor-rs never emitted them on a fixture either.

**Read the upstream `Fixed` section as an FP list.** Every "no longer reports X"
bullet is a place the port may now be strictly louder than the oracle, and the
only instrument that sees it is the sweep. Both of this bump's fixes are
upstream `Fixed` bullets; neither is visible in the snapshot diff. Step 7 (the
sweep) is therefore not the last gate but a *finding* gate, and the ritual should
be walked expecting it to send you back to step 4.
