# Upstream re-pin `v0.3.8 → v0.3.9` (2026-09-21)

**Pin `ffb456b0` (`v0.3.8`) → `d0c370f7` (`v0.3.9`)**, one release, 447 commits, branch
`upstream-pin-v0.3.9`. Verdict and numbers are in § 6.

`v0.3.9` is the last release of upstream's 0.3 line and its own release note calls it "the
largest fix batch of it: over a hundred pull requests closing false positives". Step 0 reads
that as an FP list, and the list is ~70 bullets long — so the expectation going in was a
bump dominated by RETRACTIONS, where rigor-rs keeps emitting what upstream has stopped
emitting. That is what happened, but only three shapes of it reached this port, because most
of upstream's hundred fixes are in subsystems the port does not have yet (plugins, cache,
incremental, sig-gen, coverage).

The bump's own finding is the opposite of the last one's: **the `v0.3.8` sweep budget is
gone**. `#874` fixed the mutual-recursion re-walk that made rufo's `formatter.rb` take over
an hour, and `--sweep` now runs end to end in **under three minutes** (the `mail` corpus:
2,162 s → 37 s). The ritual's "budget ~80 minutes and run the two gates in parallel"
paragraph is obsolete.

**A new pin-tracking surface appeared and is deliberately NOT vendored.**
`data/capability_roles/capability_roles.rbs` (#976) ships the five capability-role
interfaces (`_Closable`, `_RewindableStream`, `_ClosableStream`, `_FileDescriptorBacked`,
`_Callable`) into every default run, so a `%a{rigor:v1:conforms-to _ClosableStream}` resolves
with no configuration. rigor-rs has **no `conforms-to` support at all** (`grep` over
`crates/`: zero hits), so the file cannot produce a false positive here — an interface is
only reachable through a directive the port never reads, and the severity change the same PR
makes (an unresolvable `conforms-to` is a warning now, not an info) is a diagnostic rigor-rs
does not emit either. It is recorded in `UPSTREAM.md` step 3 so the next bump re-checks the
premise rather than rediscovering the file.

## 3. F-A — `declines_bot?` reaches every positive-edge carrier

`v0.3.8` already had #751's decline for the `Constant` carrier: `Bot` asserts "this can never
match", and only a KNOWN-disjoint ordering supports it. `6cde8381` lifts that test into a
shared `declines_bot?` and gives it to `narrow_shape_to_class` and
`narrow_singleton_to_class` as well — a `Tuple` projects through `Array`, a `HashShape`
through `Hash`, a `Singleton` through `Class`, so a project module mixed into any of those
leaves the ordering `:unknown` for exactly #657's reason.

Port side this is four lines in `guard_meet_precise`: the `Constant`/`Tuple`/`HashShape` arm
answers `ClassFact::Widened` on `Unknown` instead of `Bot`, and keeps `Bot` for `Disjoint`
and `Superclass`. The two facts are NOT interchangeable and rows b15b/b30b are why: `Bot` is
the join identity, so the call after the `if` still fires through it, while `Widened` absorbs
and silences it.

The SINGLETON half is deliberately not ported. `guard_meet_precise` declines a `Singleton`
carrier outright, and a probe of `case Widget when Meta` with `extend Meta` measures BOTH
engines silent — there is no witness to remove. Upstream's own residue (#898: `extend
Comparable` is orderable against `Class`, still collapses, still a reference FP) therefore
stays matched by construction.

Controls, each measured on both engines and now fixture rows 100 b41/b42/b43: a shaped
carrier under a PROVEN-disjoint guard still collapses and still fires after the `if`; a
`HashShape` twin of the same; `instance_of?` still collapses before the ordering is consulted.

## 4. F-B — dispatch on the resolved name, not the node class

Prism spells `::RUBY_VERSION` as a `ConstantPathNode` with a nil parent, so upstream's
node-class dispatch sent the rooted spelling down the curated `X::VERSION` route and declined
it: one program, two spellings of one constant, two diagnostic sets (#877). `152f7c9f`
dispatches on `qualified_name_or_nil` instead — unqualified folds when predefined, qualified
when curated.

The port's lowering already renders both spellings the way `qualified_name_or_nil` does
(`::Foo` ⇒ `"Foo"`), so the fix is to DELETE the source-spelling re-check the port carried to
model the old behaviour. But deleting it alone would have been wrong, and the must-still-fire
control is what caught it: the port's LENIENT constant rendering also drops a DYNAMIC base,
so `k::RUBY_VERSION` renders bare `"RUBY_VERSION"` too, where `qualified_name_or_nil` answers
nil. The old source-slice test was doing that second job silently.

So `Node::ConstantRead` gained a `dynamic_base: bool`, set at lowering from the STRICT
renderer (`strict_constant_path_string`, the port's existing twin of
`qualified_name_or_nil`) — a structural fact where a textual heuristic used to stand. Rows
f30/f31 (rooted `RUBY_ENGINE`, rooted operand inside the `Gem::Version` wrapper) fold with
it; rows f32/f33 (`k::RUBY_VERSION`, `Object::RUBY_VERSION`) still report on both engines.

## 5. F-C — the family only the sweep could see, and the row it nearly cost

The sweep's single FP candidate was gitlab-foss's
`lib/gitlab/duo_agent_platform/config.rb:98`, `normalized_cache.presence` reported `for Hash`
where the reference is silent. Bisected (`git bisect run`, 9 steps, presence probe) to
**`1ad7351e` (#580)**, `Inference::MutationRejoin`:

> Mutation widening was a one-way door. The first content mutation replaced the literal
> `Tuple` / `HashShape` with a `Nominal`, `widen_for_mutator` had no `Nominal` arm, and every
> later store into the same collection was invisible to content evidence.

With the re-join the later stores grow the carrier's value side, so two branch edges that
stored DIFFERENT value classes no longer carry the same instantiation; `Scope#join` leaves
`Hash[…] | Hash[…]`, `receiver_descriptor` has no union arm, and the receiver stops
witnessing. The discriminator is NOT "a store inside a branch" — the grid says so:

| shape | reference |
|---|---|
| two unconditional stores, different classes | FIRES (one edge, no join) |
| unconditional + branch store, SAME class | FIRES (the edges agree) |
| unconditional + branch store, DIFFERENT class | SILENT (the edges are a union) |

rigor-rs models exactly that difference inside the self-contained collection-carrier pass
(`collection_shape_snapshots`), whose only output is `call node -> "Array" | "Hash"`: the
accumulated set of erased store-value classes rides in the carrier nominal's `args`, so the
pass's standing identical-`TypeId` join decline does the union for free, and the members are
never read — only compared.

**Two things the first cut got wrong, both found by measurement rather than by reading.**

1. *Collapsing the join to untyped loses rows.* The first cut widened a disagreeing join to
   `untyped`, took the sweep to 0 FP — and mastodon's matched count dropped 420 → **419**.
   The lost row is `application_helper.rb:180`: a branch push makes the edges diverge, the
   UNCONDITIONAL push after it RE-JOINS them, and the reference fires on the `compact_blank`
   that follows. A mutator on a Dynamic carrier never mints, so untyped cannot recover. The
   join now keeps a real `Type::Union` of the two carriers and `widen_for_mutator` gained a
   union arm that re-joins it — which is what `MutationRejoin`'s own "`joinable_receiver?`
   skipped an already-nominal receiver, so the arm never saw the argument types it grows
   from" paragraph is about.
2. *A store's value class is a SET, not one class.* `out << (flag ? 'a' : 1)` puts BOTH
   `String` and `Integer` in the reference's union, so a later `String` store adds nothing
   and the edges agree. Naming only single classes made that row disagree and cost it
   (fixture row r15). The classifier is syntactic — literals, an array/hash literal, a local
   read through the pass's own env, and the join of a ternary's arms — and anything it cannot
   name contributes NOTHING, which is what the reference's own `Dynamic[top]` seed does: it
   is in every instantiation and so never separates two of them.

The residue is real and it cuts BOTH ways — probed, not assumed:

```ruby
h = {}; h['a'] = 1.to_s;  h['b'] = 'x'   if flag; h.frob  # ref FIRES, port SILENT (lost row)
h = {}; h['a'] = 'x';     h['b'] = 'y'.to_i if flag; h.frob  # ref SILENT, port FIRES (FP)
```

The reference's typer names `1.to_s` as `String`, so its two edges AGREE and it reports;
this pass names nothing there, so its edges differ and it declines. The second line is the
same gap mirrored into the FP direction. Closing either needs the store value's INFERRED
type, which this pass does not have — filed as its own issue. The sweep measures the residue
at zero on 9,337 files, which is a statement about the corpus, not about the model.

What the residue does NOT cover any more: `true` / `false` / `nil`. The first cut left them
unnamed on the theory that the reference joins them through `bool`; probing says otherwise —
the reference's union carries `… | TrueClass`, so two `true` stores agree and a `true` /
`false` pair does not. Naming them closed a live FP shape (fixture rows r16–r18).

**The port's three fixes removed exactly the FP rows and no matched row.** Per-corpus matched
counts before and after the F-C fix are identical everywhere except gitlab-foss, which loses
precisely the one FP row (1,088 → 1,087), and mastodon, which ends where it started (420)
once the union re-join was modelled.

The raw bump — same port, new reference — measured **3 fixture FPs + 1 sweep FP**, the
gentlest bump since `v0.3.1` despite being the largest `Fixed` list upstream has shipped.
The reason is structural, not luck: most of `v0.3.9`'s retractions are in plugin, cache,
incremental and sig-gen code paths this port has not built, and its inference retractions
(block returns, in-place mutation, implicit-self resolution) mostly retract diagnostics
rigor-rs never emitted — they show up as the 892 gap baseline moving, not as FPs.

Corpus file counts moved 9,204 → 9,337 because the survey checkouts themselves grew since
2026-09-09 (dependabot-core 1,650 → 1,781, net-ssh 180 → 181, haml 51 → 52); the gap total
892 is therefore not directly comparable with 799.

**Incidental fix, and a caution for anyone reading an old baseline:**
`gap_census.py`'s per-corpus line counted rows by the target's BASENAME, and two members of
the standing set end in `lib` — so `rigor-survey/haml/lib` printed `gitlab-foss/lib`'s rows
again under its own name (164 where it has 2). The reported TOTAL was always right; only the
per-corpus line was wrong.
