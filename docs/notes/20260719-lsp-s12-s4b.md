## What this slice does and does NOT deliver

**Delivered**: the LSP's `SourceIndex` is now **the same index `check` builds** for
the same file set — the cross-file substrate, live, without a save. That is the
claim the parity test pins.

**NOT yet delivered**: end-to-end diagnostic equality with `check` in general.
`compute_diagnostics` still stops short of `check`'s stage-3 tail:

- **ADR-8 severity stamping.** `check` runs `severity::resolve` over the profile +
  user overrides + bleeding-edge overrides, and **DROPS** any diagnostic that
  resolves to `Off`. The LSP applies neither, so the divergence is a **presence**
  mismatch, not merely a severity one: a rule the active profile turns off is
  still published to the editor.
- **Bleeding-edge plumbing.** `check` gates `static.value-use.void` on the
  resolved severity; the LSP has no equivalent, so that rule never runs there.

Both are pre-existing (they predate S4b) and out of this slice's blast radius, but
they are the remaining gap between "same index" and "same diagnostics" —
**tracked as the stage-3-tail follow-up**. The parity tests in
`tests/lsp_check_parity.rs` are exact today because their fixtures use rules whose
resolved severity matches the authored one.

## Overlay structure

- **`ProjectContext` (tier 1)** gains `overlay: Option<ProjectFiles>` —
  `Vec<(canonical PathBuf, Arc<LoweredAst>)>`, one entry per analysable project `.rb`
  file. Discovery is bare-`check`'s (ADR-0040): the config `paths:` roots expanded
  recursively, sorted per root, minus `exclude:` and ERB templates; parse+lower is
  rayon-parallel and per-file panic-isolated exactly like `check`'s stage 1.
- **`build_overlay`** also runs the tier-1 `SourceIndex::build_project` and TIMES
  it. The resulting index is **discarded**: every dispatch rebuilds with the
  buffer's AST swapped in, so a stored copy would only cost memory. What tier 1
  keeps is the ASTs (the rebuild input) and the timing (the guard input).
- Built at startup in `run_stdio` and inside the existing **synchronous**
  `invalidate` — so a SAVED edit to a non-open project file re-harvests the ASTs
  and moves the open buffers' diagnostics (the pay-off S4 explicitly deferred).
- **Per dispatch (diagnostics only)**, on the rayon worker: `overlay_source_index`
  rebuilds `SourceIndex::build_project` over the held ASTs with the buffer's
  file's AST **REPLACED** by the buffer's freshly-lowered one, then the existing
  `analyze_with_source_and_folder` runs against it. The buffer's on-disk identity
  is its **canonicalized** `file:` path (both sides canonicalized, so a symlink or
  a `..` segment cannot smuggle the same file in twice under two spellings);
  percent-escapes are decoded. A buffer with no on-disk identity (unsaved,
  `untitled:`, or outside `paths:`) is **appended** — exactly the index `check`
  builds when that file is added to the run.
- **REPLACE, not ADD, is the FP-safety pin** and is tested directly (below):
  double registration would leave two competing method/return facts for one class
  and could resolve a name the user just renamed away — a wrong type, i.e. a false
  positive. Not traded for speed.
- **[revised — review B1]** "No on-disk identity" must not be confused with "the
  file is gone". `fs::canonicalize` needs the WHOLE path to resolve, so a buffer
  whose file was deleted or renamed on disk while it stayed open (a `git checkout`,
  a `git stash`, an IDE rename) failed it — and the resulting `None` sent it down
  the APPEND path while tier 1 still held that path's stale on-disk AST. That is
  the double registration above, reachable in ordinary editor use and **permanent**
  for clients that do not accept watched-files dynamic registration. Fixed by
  resolving the PARENT directory and re-attaching the file name; only a path whose
  parent is also unresolvable is `None`. Regression test:
  `integration_s4b_deleted_on_disk_file_still_replaces_never_appends`
  (verified non-vacuous — it fails against the old one-line body).
- **[revised — review N1]** The tier-1 `CoreIndex` is built from
  `Config::effective_plugins` (config `plugins:` **plus** the ADR-72
  `Gemfile.lock`-gated overlays), exactly as `check`'s `analyze_files` does. The
  bare `cfg.plugins` made the editor miss activesupport's core-ext reopenings on
  the most common Ruby project shape: `"s".blank?` fired `undefined method` in the
  editor while `rigor check` was silent. Pinned end-to-end by
  `lsp_applies_the_same_gemfile_lock_plugin_overlays_as_check`.
- **Buffers outside `paths:` are a deliberate divergence** (review N5). A file the
  project index does not contain — `spec/foo_spec.rb`, a scratch file — is
  APPENDED to the project ASTs, so it is analysed **against the full project
  index**, whereas `rigor check spec/foo_spec.rb` would build an index from that
  one file. The editor's answer is strictly better informed (and equals
  `rigor check lib spec/foo_spec.rb`), but it is NOT the same answer as the
  single-file CLI invocation, and the parity claim above is scoped to files inside
  `paths:`.
- **hover / completion / documentSymbol keep the single-file index** in v1, per
  the spec: they are answered synchronously on the loop thread under a <100 ms p95
  budget that cannot absorb a project rebuild, and a saved-state project index
  would answer from stale facts after an edit.

## Scale guard **[revised — hysteresis, review N2]**

The original single-sample sticky trip was fragile and is replaced. Data: on an
idle machine at 3 117 files, six consecutive `build_project` runs were
93.9 / 93.7 / 90.9 / **106.2** / 94.7 / 92.9 ms against a 100 ms budget — a
1-in-6 false trip on one sample; and the same quantity measured
236.9 / 145.4 / 484.6 ms across three machines (3.3× spread). **One sample is not
a classifier**, and sticky-for-the-session made it a per-session coin flip with no
recovery.

The guard now has **asymmetric hysteresis**:

- **Samples come from builds that happen anyway.** While the overlay is ON, the
  per-dispatch `build_project` is timed in `overlay_source_index` and carried back
  to the loop on `Computed.overlay_build` — free, since the dispatch builds it to
  analyse. While OFF, the sample comes from the tier-1 build at a **structural**
  `invalidate`. Startup counts as the first sample.
- **ASYMMETRIC hysteresis.** Disable after `OVERLAY_GUARD_STRIKES` = 2 CONSECUTIVE
  over-budget samples; **re-enable on a SINGLE** under-budget one. Any under-budget
  sample resets the streak, so an isolated spike among healthy samples can never
  accumulate into a trip. Disabling must resist a transient stall; re-enabling is
  cheap to undo, because once ON per-dispatch samples are plentiful and a wrong
  re-enable self-corrects within two dispatches. Symmetry was also *wrong*: while
  OFF the only samples come from structural invalidations, so requiring two
  consecutive ones made recovery near-unreachable and the "no restart needed"
  disclosure effectively false.
- **Worker samples are IGNORED while the guard is disabled.** A sample arriving
  once the overlay is off necessarily comes from a dispatch that PREDATES the
  disable-swap (a concurrent per-URI dispatch, a buffer closed mid-flight), so it
  describes a posture that no longer exists. Acting on one was terminal: it
  re-enabled the guard while `project.overlay` was still `None`, and with no
  overlay no further sample is ever produced — the session could never actually
  recover, while telling the user it had ("re-enabled … for 0 files", the count
  read from the already-emptied overlay). Recovery therefore lives in `invalidate`,
  where the overlay is being rebuilt anyway and the disclosure can report the NEW
  overlay's count.
- On disable the held ASTs are dropped (no overlay ⇒ no reason to hold them) and
  the context is swapped with a **bumped generation**, so the 3-axis stale-drop
  handles in-flight workers with no new concurrency reasoning.
- The `window/showMessage` (WARNING) names the measured cost, the budget and the
  strike count, and states what actually restores it: saving a config or signature
  file re-measures, and **one** under-budget rebuild restores cross-file
  diagnostics — no restart. An EMPTY project neither feeds the guard nor discloses.

Because the startup sample alone can never disable, **a session always starts
cross-file** and only steps down when a real dispatch confirms the cost.

### Verifying it does not coin-flip

40 consecutive `build_project` samples at 3 117 files (median 66.1 ms, min 63.6,
max 93.5 — i.e. containing exactly the kind of outlier that burned the old guard):

| budget placement | 1-sample trips | **2-consecutive trips** |
|---|---|---|
| at the median (worst case for any classifier) | 19/40 (48 %) | **11/39 (28 %)** |
| median + 3 % | 8/40 (20 %) | **3/39 (8 %)** |

And on the reviewer's own straddling series (93.9 / 93.7 / 90.9 / 106.2 / 94.7 /
92.9 vs 100 ms): **1-sample trips 1/6; 2-consecutive trips 0/5** — the outlier no
longer disables anything.

At the REAL operating points the classification is unambiguous in both directions:
**0/40 samples over budget at 3 117 files** (stays on) and **6/6 over at 4 675**
(disables). The residual risk is confined to projects sitting within a few percent
of the budget — and there the symmetric re-enable means a wrong call self-corrects
instead of persisting for the session.

The guarded quantity remains a good proxy for what it protects: tier-1
`build_project` tracks the per-dispatch rebuild within ~15 % (68.4 vs 58.0 ms at
3 117 files; 145.4 vs 135.5 at 4 675) and errs high — conservative-safe.

## Invalidation cost **[revised — review N3]**

S4 approved a **synchronous** `invalidate` on the loop thread when it was a
`CoreIndex` rebuild on a rare trigger. S4b made that ~20× more expensive (it
re-read, re-parsed and re-lowered the whole project) while `watched_file_is_relevant`
fired it for **any** `.rb` — i.e. every source save, on the thread that owes
hover/completion a <100 ms p95. The premise had broken.

Watched-file changes are now **classified by cost**: `.rigor.yml` / `Gemfile.lock`
/ `sig/**/*.rbs` keep the full `invalidate` (structural changes are genuinely rare,
which is what made S4's decision sound), while `.rb` saves go to
`reharvest_sources`.

### The invariant, and the conservative rule that satisfies it

**The incremental state must be byte-identical to what a full rebuild would
produce.** The first implementation tried to satisfy it with a `ProjectScope`
predicate re-deriving bare-`check`'s discovery rule, and diverged from it four
ways — a deleted DIRECTORY (the path stops resolving, so the stale AST was never
removed), a symlinked `.rb` (harvested by `Dir.glob` semantics but held under its
out-of-`lib` CANONICAL path, so the predicate rejected it and every save removed
it), `paths: ["."]` (`rel.starts_with(".")` is false for every relative path, so
the first save dropped everything), and — found by the differential test below —
the same canonical path held TWICE (under `paths: ["."]` a symlink and its target
are both walked), where only the first occurrence was updated.

Four divergences say the predicate is the wrong shape. A predicate that must agree
with a tree walk will keep drifting from it, so it is **deleted**; the rule is now:

- **Replace in place ONLY when the changed path resolves to an entry ALREADY
  HELD**, looked up by canonical path, keeping its original position — and
  updating **every** matching position, since duplicates are legitimate. A held
  entry whose file is confirmed gone is removed in place.
- **EVERY other case falls back to `apply_full_overlay_build`**: an unresolvable
  path, a path not currently held (it could be a new in-scope file), a read/parse
  failure, an unparseable URI, anything ambiguous. Correct by construction — there
  is no membership predicate left to keep in sync with discovery.
- An event is IGNORED only when BOTH its canonical form is not held AND its path
  (decoded *or* canonical) is not under any configured root. `touches_configured_root`
  is deliberately one-sided — it answers "is it safe to ignore this?", so every
  uncertainty answers "no" and costs at most one full rebuild. It never decides
  that a file *belongs* in the index.

No `CoreIndex` rebuild on either path: it depends on the plugin set and the
signature dirs, neither of which a project `.rb` can change.

### Measured per-save cost on the loop thread

| corpus | files | fast path (held entry) | fallback (full rebuild) |
|---|---|---|---|
| mastodon/app | 1 236 | **0.098 ms** | 48.0 ms |
| gitlab-foss/lib/gitlab | 3 117 | **0.210 ms** | 120.9 ms |
| gitlab-foss/lib | 4 675 | **0.258 ms** | 256.3 ms |

The fast path — saving the file you are editing, the overwhelmingly common event —
is ~575× cheaper than the rebuild it replaced at 3 117 files. It is slightly more
expensive than the pre-review measurement (0.067 → 0.210 ms) because the table is
now scanned for **all** matching positions rather than the first, plus one
`canonicalize`; that is the price of the duplicate-path correctness above, and it
is irrelevant against the `<100 ms p95` hover/completion budget the change exists
to protect.

### The differential test

`incremental_reharvest_is_byte_identical_to_a_full_rebuild` asserts the invariant
in its strong form: after each of seven mutations it compares a **complete
fingerprint** of the held table — every entry's path AND its AST's full `Debug`
dump, IN ORDER — against a fresh `build_overlay` of the same tree, under BOTH
`paths: ["lib"]` and `paths: ["."]`. The sequence covers edit, edit-via-symlink,
delete, create, **directory deletion**, an unrelated out-of-project file, and a
mixed batch. It fails on ANY divergence, not just the ones that were found — which
is how the duplicate-canonical-path bug surfaced.

## Acceptance results

1. **Parity with `check` — the keystone. PASS, end-to-end against the real
   binary** (`crates/rigor-cli/tests/lsp_check_parity.rs`): two processes, same
   on-disk project, `RIGOR_NO_RUBY=1` on both for a hermetic posture. Fixture:
   `Base#helper` public in `lib/base.rb`, `Sub` overriding it private in
   `lib/sub.rb` ⇒ `def.override-visibility-reduced`. The test asserts
   (a) `rigor check lib/sub.rb` (single file) is **silent** — so the finding is
   purely cross-file and the comparison cannot pass vacuously; (b) `rigor check
   lib` reports exactly one finding; (c) the LSP's `publishDiagnostics` for the
   SAVED buffer equals it on **(line, column, severity, message)**.
   A second in-process version (`integration_s4b_saved_buffer_matches_project_check_not_single_file`)
   compares against an independently-assembled stage 2+3 and additionally asserts
   the pre-S4b single-file path returns nothing.
2. **Dirty-buffer overlay. PASS** — renaming the overriding method away in the
   OPEN BUFFER clears the finding with no save (the test re-reads the on-disk file
   to prove it was never written), and restoring it in the buffer refires it.
3. **REPLACE, not ADD. PASS** — on-disk `lib/main.rb` has `Api#fetch -> String`
   plus `Api.new.fetch.lenght` (fires `call.undefined-method`); the buffer renames
   the DEF to `grab` and keeps the call site. Under REPLACE `Api#fetch` is gone,
   the in-source receiver goes lenient, and the publish is EMPTY. Under ADD the
   on-disk AST would still supply `Api#fetch -> String` and the stale finding would
   keep firing — verified with the CLI: a `lib/` holding BOTH versions reports the
   error, the renamed file alone does not. So the assertion genuinely discriminates
   the two semantics.
4. **Guard. PASS [revised]** — `overlay_budget = Duration::ZERO` makes every
   sample over-budget by construction (no wall clock, threshold or corpus size is
   raced). The test now pins the hysteresis end to end: the startup sample alone
   does NOT disable (the first publish still carries the cross-file finding), the
   first dispatch is the second consecutive sample and trips it, the WARNING
   `window/showMessage` says both "single-file scope" and "no restart needed", and
   the NEXT dispatch has lost the cross-file finding — i.e. the fallback really
   took effect. `integration_s4b_guard_stays_enabled_on_a_healthy_project` is the
   complement: under a generous budget the overlay survives six dispatches with no
   drift and no message churn. `overlay_guard_needs_consecutive_samples_in_both_directions`
   unit-tests the state machine, including "spike, good, spike does not disable"
   and the symmetric re-enable.
5. **S1–S4 preserved. PASS** — all 43 pre-S4b lsp tests unchanged and green
   (debounce, 3-axis stale-drop, single-writer, invalidation, no-lost-update,
   panic-never-stuck, shutdown-no-hang), plus
   `integration_s4b_watched_file_save_reharvests_the_project_asts` proving the S4
   invalidation plumbing carries the S4b substrate, and
   `integration_s4b_source_save_reharvests_only_that_file_and_deletion_removes_it`
   driving edit / restore / **delete** / re-create through the narrowed (N3) path —
   the delete transition being what a replace-only incremental update silently gets
   wrong.

## Non-flaky test approach + 5× result

Same bar as S2/S3/S4: **no wall-clock races**. The new seams are both INJECTED,
not timed:

- **`ServerContext::project_root`** — a real on-disk temp project (unique per test:
  pid + a process-global counter, removed on drop) instead of mutating the
  process-global cwd, so the suite stays parallel-safe.
- **`ServerContext::overlay_budget`** — the guard test forces `Duration::ZERO`
  rather than building a corpus big enough to blow a real threshold.
- Tests that only `didOpen` use a **30 s debounce** so no stray timer can
  interfere; the two dirty-buffer tests use the existing 10 ms pattern and assert
  on the publish that arrives (`recv_diags` waits up to 10 s), never on a
  no-arrival window.
- `Harness::start_full` (every pre-S4b test) now points at a nonexistent root ⇒
  zero project files ⇒ overlay OFF ⇒ those tests keep the exact single-file
  behaviour they were written against.

- The guard tests never race a real threshold in EITHER direction:
  `Duration::ZERO` makes every sample over-budget by construction, and
  `Duration::from_secs(30)` makes every sample under-budget — so the hysteresis
  transitions are exercised without depending on how fast the machine is.

**5× flake check:** the lsp test binary (`lsp::`, now **59** tests) ran **59/59
five times, 0 failures**, and **59/59 once with `RAYON_NUM_THREADS=1`**. The E2E
`lsp_check_parity` tests (now 2) ran 5×, 2/2 each time.

## What the deferred `extend_with` API would still unlock

The spec deferred `SourceIndex::extend_with(&mut self, ast, core)` (with its
pass-ordering risk — `build_project`'s later passes, notably the lexical override
index, may depend on complete earlier-pass state). The measurements say what it is
worth:

- **5 k-file projects.** The whole per-dispatch cost IS `build_project`
  (135 of 135.5 ms at 4 675 files; lower and analyze round to 0.0). An O(1-file)
  extension would remove the guard's reason to exist and give gitlab-scale
  projects cross-file diagnostics.
- **Cross-file hover / completion.** Blocked purely on cost: they run
  synchronously on the loop thread under <100 ms p95, and a rebuild is 20 ms at
  1.2 k / 58 ms at 3.1 k — too much to spend per keystroke-adjacent request.
- What it would NOT change: the 244-file and 1.2 k cases are already 0.6 ms and
  20 ms — the overlay is free there.

**Not a gap: the single-buffer overlay.** v1 overlays only the DISPATCHING
buffer's own file; other open dirty buffers are represented by their SAVED state.
That was previously listed here as a limitation — it is not. Their saved state is
exactly what `check` sees, so single-buffer overlay is **parity-preserving by
definition**. Overlaying every dirty buffer would make the editor's answer diverge
from `check`, which is a different (arguably desirable) product decision, not a
correctness debt.

## Known limitation: project root **[deferred — review N4]**

`run_stdio` hardcodes the overlay's root to the process cwd (`PathBuf::from(".")`)
and never consults `initialize`'s `rootUri` / `workspaceFolders`. A server launched
from the wrong directory therefore discovers **zero project files**, silently falls
back to the single-file index — and, because an empty project deliberately does not
trip the scale guard, emits **no disclosure at all**. Deferred to a follow-up
(honouring `rootUri` and disclosing an empty discovery), recorded here so it is not
rediscovered as a mystery.

## Where the mini-spec was imprecise (and what was built instead)

- Acceptance 1 says "LSP diagnostics == `rigor check <file>` diagnostics".
  `rigor check <file>` on ONE file builds its project index from that file alone,
  so it has no cross-file context either and cannot exhibit the "cross-file context
  changes the answer" case the same bullet demands. The test therefore compares
  against **`rigor check <project>`, restricted to that file's rows** — the only
  reading under which the bullet is self-consistent — and asserts the single-file
  run is silent, which pins the intent (the pre-S4b LSP fails).
- Acceptance 3 says "renaming a **method**". A method rename only discriminates
  REPLACE from ADD when the on-disk definition supplies a fact the buffer's version
  removes; the `Api#fetch -> String` return-typing fixture above is such a case and
  is what the test uses (a class rename would work identically).
- **The spec's scale guard did NOT hold.** A single `build_project` sample,
  sticky for the session, is not a classifier for a quantity with this much
  run-to-run and machine-to-machine variance; and S4's synchronous-rebuild premise
  broke once S4b made the rebuild 20× more expensive on a per-save trigger. Both
  are corrected above (hysteresis; narrowed invalidation).
- Everything else in the spec held: the architecture, the swap-and-rebuild
  decision, the 100 ms budget VALUE, the hover/completion carve-out, and the
  extend-API deferral all stood up unchanged.
