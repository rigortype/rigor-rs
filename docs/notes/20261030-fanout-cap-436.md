# Reaching-write fan-out cap (#436): outcome

#436 is the residue of #422. After the `local_reach` memo (stack #434), two of
parser's generated lexers still took more than 1,600 s each, so a `check` of
the 16,623 installed-gem files never finished. PR #440 landed a fan-out cap.
It was Approved in review round 1.

## Fix

`local_reach_uncached` (`crates/rigor-infer/src/reach.rs`) answers
`(Reach::UNKNOWN, None)` when more than `MAX_REACHING_WRITES` writes of the
local reach the read. The cap is a `const` set to 256.

- **What W counts:** the writes that survive the collector's read-dependent
  filters (`dead.write_reaches`, the closure test, the own-RHS test). It is
  counted before the definite-assignment cut and before the after-the-read
  skip.
- **Where the check sits:** after the event loop, so the `for`-index,
  rescue-binding and guard returns keep their answers.
- **The comparison is `>`:** 256 writes fire and 257 decline.
- **Locals only.**

This ports the reference's budget principle: an unbounded join returns the
gradual floor (`inference-budgets.md:46`). The reference itself has no backward
walk to bound.

## Measured

**Fan-out W per read, on an instrumented build:**

| set | max W |
|---|---|
| standing sweep (it includes mail's vendored rdoc) | 176 |
| the 16,621 other gem files | 176 (rdoc `markdown.rb`) |
| parser `lexer-F0.rb` / `lexer-F1.rb` | ≥ 437 / ≥ 691 |

The issue's "sweep max 35" missed `vendor/bundle`: `fp_audit` globs
`**/*.rb`.

**Time:**
- lexer-F0 went from more than 1,600 s to 0.19 s, and lexer-F1 to 0.17 s.
  Their max RSS is 57–62 MB.
- All 16,623 gem files check in 9–10.5 s, exit 1.
- The issue's 31 s figure was measured under contention.

**Output:**
- The port-vs-port self-diff against master is byte-identical by `cmp` on the
  8 corpora and the 16,621 gem files master finishes.
- The lexers add one subset diagnostic each.
- The memo audit (`RIGOR_REACH_MEMO_AUDIT=1`) is byte-identical with 0 panics.
- The sweep is 0 FP / 9,435 / 828, which is master's gap set.

## The cap is not purely a decline

The brief argued that `UNKNOWN` is every consumer's decline. That holds for
the value but not for its effects. The review and the design companion found
two ways a cap mints a diagnostic:

1. **#442.** A capped top-level `if` predicate no longer folds. The arm the
   reference treats as dead is then live, and it loses its narrowing:
   `v = nil; if v; v.zz; end` followed by 256 writes fires `zz for nil`.
   Def bodies were clean in every probe.
2. **#437/#435.** Skipping a nested walk changes which walk first visits a
   predicate fold, and the fold memo is order-dependent. In a def with W > 256,
   the head fires #435's existing FP where master was accidentally silent
   (row `x6`).

Neither occurs in any measured real file. Both were filed and the PR landed,
following the review merge bar.

**Lesson:** a decline at one consumer can widen what another consumer sees.
Probe the shapes where the declined value feeds dead-code or narrowing
decisions, not just the value's direct users.

## Not closed: the sub-cap band (#441)

Below the cap the walk still costs about W^4. `onevar_48` (W = 49) takes 3.4 s
and `onevar_96` takes about 60 s, on master and on the head alike. No real
file sits in the band.

The companion measured an exact fix: break the write loop once the answer is
saturated, which brings `onevar` W ≤ 128 to 0.10 s and the uncapped lexers
under 1 s. It moves fold first-visits in the same way the cap does, so it
waits for an order-independent fold memo (#437, gated on #435).

Also filed: #443, a pre-existing master FP. An argument read in a
reference-dead `if v == 2` arm skips the dead-arm narrowing.
