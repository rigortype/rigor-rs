# Upstream re-pin `v0.3.1 → v0.3.2` (+ rbs 4.1.0 → 4.1.1)

**2026-08-09.** Pin `c39e6675` (`v0.3.1`) → `c6b91b9e` (`v0.3.2`). Verdict:
**0 FP / 9204 files, gaps 1125 → 841 (−284)**, harness PASS with the divergence
registry EMPTIED. The bump is unusual in three ways, and each one is the reason
this note exists rather than a ledger line: the rbs half is a pure version-string
change, the *overlay* half moved instead, and the change closed the whole
`UNBUILDABLE_DEFINITIONS` table.

## What actually moved

| axis | v0.3.1 | v0.3.2 | effect |
|---|---|---|---|
| reference | `c39e6675` | `c6b91b9e` | −295 reference-side possible-nil FPs (#297), +11 gaps from un-blinding (#300/#301) |
| rbs | 4.1.0 | 4.1.1 | **none** — `core/` + `stdlib/` byte-identical |
| overlay (`data/`) | — | 5 files rewritten, 2 dirs added | the real work |
| `UNBUILDABLE_DEFINITIONS` | 12 entries | **0** | rigor-rs resumes witnessing |
| divergence registry | 1 entry (#237) | **0** | upstream fix is an ancestor |

### The rbs bump is a no-op, and that is *checked*, not assumed

`python3 harness/vendor_rbs.py <rbs-4.1.1-gem> --check` →
`CHECK: committed tree matches this source exactly` (49 libs, 174 `.rbs`). The
committed tree was generated from 4.1.0; it matches the 4.1.1 gem byte for byte.
So the RBS-bump hazard from the `v0.3.1` bump
([note](20260731-upstream-pin-v031-rbs41.md)) — "an RBS bump is not data-only" —
does not apply: no signature moved, so no signature-resolution behaviour can
have moved, and any test movement traced to RBS would have been a stop-and-report.
None occurred. Only `PROVENANCE.md`'s version/path/date changed.

### The overlay moved instead — and the ritual had no step for it

`vendor_rbs.py` carries `overlay/` across untouched by design, because that half
tracks the REFERENCE pin, not the rbs version. The bump ritual in `UPSTREAM.md`
said "re-sync `vendor/rbs/overlay/` from the reference's own `data/`" in one
clause and left the mechanics to the reader. Doing it by `diff -r` rather than by
copying the one file the survey had named turned up five rewritten files and two
new directories, not one:

- `core_overlay/resolv.rbs` — NEW. Inert here (`resolv` is in
  `DEFAULT_LIBRARIES`, so the reference's new load gate is satisfied on both
  sides); provenance fidelity only, as expected.
- `vendored_gem_sigs/racc/` — NEW and load-bearing. `nokogiri.rbs` declares
  `class Nokogiri::CSS::Parser < Racc::Parser`, and a declared superclass with no
  declaration anywhere raises `NoSuperclassFoundError` and took the whole
  definition to `Dynamic[top]` (upstream #299).
- `vendored_gem_sigs/{bundler,rubygems}/` — REWRITTEN by #300/#301 to stop
  re-declaring anything the `rbs` gem's `sig/shims/` already declares.
- `core_overlay/{pathname,string_scanner}.rbs`, `vendored_gem_sigs/cgi/` —
  comment-only changes documenting the new load gates
  (`LIBRARY_SUPPLEMENT_CORE_OVERLAYS` / `…_VENDORED_DIRS`).

`PROVENANCE.md` now carries the executable re-sync recipe, so the next bump does
not depend on someone thinking to run `diff -r`.

## The one real hazard: a shim asymmetry the sweep cannot see

#300/#301 make the reference's `data/vendored_gem_sigs/{bundler,rubygems}/`
**depend on** the `rbs` gem's `sig/shims/{bundler,rubygems}.rbs`. The reference
reads those shims on every run (`rbs` is in `Environment::DEFAULT_LIBRARIES`, so
its whole `sig/` tree loads), so after the rewrite they are the ONLY declaration
site for `Bundler.definition`, `Bundler.default_lockfile`,
`Bundler::Definition#lockfile`, `Bundler::LockfileParser#specs`,
`Gem::Specification#name`, `Gem::Specification#version` and friends.

rigor-rs deliberately does not vendor the `rbs` gem's `sig/`. So syncing only the
`data/` half would have made rigor-rs's surface **strictly weaker than the
oracle's** on exactly the classes this bump un-blinds — the classic FP shape.

**Measured, on a hand-written probe against the oracle:**

```
rigor-rs: shim.rb:1:13: undefined method `definition' for singleton(Bundler)
          shim.rb:5:11: undefined method `default_lockfile' for singleton(Bundler)
oracle:   (silent on both)
```

Two live false positives. **The 9204-file sweep reports 0 FP with them present**,
because no corpus file calls those methods — the same fixture-corpus blind spot
recorded in [the survey-FP triage](20260731-survey-fp-triage-24.md), now
reproduced on the sweep set. A green gate was not evidence here.

Fix: vendor `sig/shims/` (3 files) as `overlay/rbs_shims/`. Only `sig/shims/` —
the rest of the gem's `sig/` would drag `RBS::*` into `knows_class`, the failure
mode `PROVENANCE.md` records for the `prism` supplement (8 fresh FPs). After the
copy the probe is silent on both sides, and the sweep is unchanged at 0 FP / 841
gaps — i.e. the shims cost nothing measurable and close an off-corpus FP class.

`enumerable.rbs` is copied with them for fidelity (it is an `| ...` overload
continuation narrowing `Enumerable#each_slice(2)` to a tuple); measured
separately, it moves nothing on the sweep.

**`BigMath` needed the environment check, and passed it.** It was the table's
only `[env]`-keyed member ([note](20260731-bigmath-ingestion-asymmetry.md)): with
the `bigdecimal` gem absent, `v0.3.1` already built it and the set was 11. Here
`gem list bigdecimal` → `4.1.2, 4.0.1`, i.e. the gem IS installed and the entry
still went away. So this is a PIN change, not a gem change — the environment
caveat is preserved in the doc comment for whatever re-populates the table next.

The recapture is real but small on the sweep: fixture 78 gains 3 diagnostics
(`BigMath.frobnicate`, `BigDecimal#frobnicate`, `Bundler.frobnicate` now
witnessed), while the ~16 `Gem::`/`Bundler` rows still in the census are a
different mechanism — receiver types rigor-rs does not resolve
(`Bundler::Source::Git`, `Gem::BasicSpecification`) and `call.wrong-arity` on
`Gem::Specification.new` — not blinding. **The survey's predicted ~11-row
recapture did NOT materialise**; the measured total is 841, exactly the survey's
pre-recapture figure.

## Fixture 79 kept, not deleted (deviation)

The plan said to delete `harness/corpus/79_sig_undeclared_type_ref.rb` with its
registry entry. Only the entry was removed. `9515c8f8` (upstream #237) is an
ancestor of `v0.3.2`, so the reference now emits the same `call.undefined-method`
rigor-rs does: the fixture stops being a divergence and becomes positive parity
coverage. It is also one of the very few fixtures exercising project-`sig/`
behaviour, which **neither sweep tool can see** (both sides run core+stdlib only
from a clean cwd — [CORPUS.md](../../harness/CORPUS.md)). Deleting it would have
traded a green gate for a real coverage hole.
